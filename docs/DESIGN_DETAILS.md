# Design Details

## 1. 设计目标

本项目当前版本的设计重点不在“单次把 SQL 生出来”，而在下面几个原则：

1. 结构化
2. 可追踪
3. 可审阅
4. 可扩展
5. 尽量减少无效上下文

## 2. 为什么要拆成 Planner + Phase

如果直接让单个模型从需求一步到位写 SQL，会遇到几个问题：

1. 上下文过长
2. 不同阶段关注点混在一起
3. 用户很难在中途纠偏
4. 错误很难归因

因此项目采用：

1. Planner 负责“决定做什么”
2. Phase 节点负责“按计划生成什么”

这使得：

1. 计划可以单独审阅
2. 不同阶段可以并行
3. 后续执行失败时更容易定位到哪个阶段的问题

## 3. 为什么所有关键输出都结构化

项目中大量使用 Pydantic 模型，而不是自由文本，原因是：

1. 结构化输出更适合下游节点读取
2. 避免后续节点再次从长文本里猜意图
3. 更容易做日志、测试和 diff
4. 更适合后续接 repair loop 和自动验证

典型结构化对象包括：

1. `PlannerOutput`
2. `PhasePlan`
3. `PhaseResult`
4. `ExecutionResult`

## 4. 为什么知识获取做成运行时工具

### 4.1 旧问题

如果在一开始把所有资料都塞进上下文，会有这些问题：

1. token 消耗高
2. 不相关知识干扰推理
3. 阶段之间重复携带相似上下文

### 4.2 当前方案

系统改为：

1. 先给出结构化计划
2. 节点自己发现知识缺口
3. 节点在需要的时候再调用知识工具
4. 知识可以多轮增量补充

### 4.3 当前工具设计

- `inspect_known_evidence`
  - 看已知上下文
- `list_available_topics`
  - 看知识库主题目录
- `retrieve_knowledge`
  - 真正从 KV Store 检索 evidence

### 4.4 为什么保留 `KnowledgeBundle`

因为单次检索不够，系统必须支持：

1. 多轮检索
2. 多轮合并
3. 检索历史保留
4. 明确哪些 topic 仍缺失

## 5. 为什么 CLI 审批放在 planner 和子计划阶段

这是为了把用户介入放在“代价最低但影响最大”的位置。

### 5.1 如果太晚介入

等 SQL 全部生成后再反馈，问题是：

1. 很多错误已经固化
2. 修改成本高
3. 需要回滚更多下游步骤

### 5.2 当前审批点的价值

- Planner 审批
  - 确认测试目标、覆盖范围、对象命名、阶段契约
- 子计划审批
  - 确认每个阶段的具体职责和知识需求

这样可以让用户先把方向纠正，再进入 SQL 生成。

## 6. 为什么节点要支持独立 provider

这个设计是为了避免以后被单一模型策略卡死。

### 6.1 当前收益

1. 不同节点可以绑定不同 key
2. 不同节点可以绑定不同模型
3. 更容易做成本和质量平衡

### 6.2 未来收益

1. planner 可以用更强模型
2. critic 可以用独立模型
3. 某些阶段可以用更便宜模型

## 7. 为什么保留 mock executor

因为当前阶段的主要验证目标不是数据库正确性本身，而是：

1. 流程是否跑通
2. 审批回路是否能闭环
3. 输出结构是否稳定
4. 日志和产物是否完整

等这些稳定之后，再接真实数据库执行器更合适。

## 8. 为什么保留样例脚本和 smoke test

样例和 smoke test 的目标不同：

### 8.1 smoke test

关注：

1. 编排是否可运行
2. 输出是否能落盘
3. 交互回路是否能正常走完

### 8.2 sample cases

关注：

1. 给后续迭代展示一个输入输出范例
2. 方便观察当前结构化产物长什么样
3. 为将来的回归样例体系打基础

## 9. 当前架构的主要扩展点

### 9.1 执行器扩展点

可以把 `MockSqlExecutor` 换成：

1. 真正的数据库执行器
2. 带错误路由的执行器
3. 自动重试和 repair 执行器

### 9.2 知识层扩展点

可以把本地 JSON KV Store 扩展为：

1. 多文件知识库
2. 分版本知识库
3. 远程服务
4. 检索增强系统

### 9.3 UI 扩展点

CLI 现在只是第一版，可以继续增强：

1. 展示更多状态
2. 展示知识检索明细
3. 展示节点执行耗时
4. 支持更复杂的审阅动作

### 9.4 Planner 扩展点

可以进一步拆成：

1. 多 planner 并行草案
2. 多 critic 投票
3. 最终裁决 agent

## 10. 维护建议

### 10.1 开发时优先遵守

1. 新节点尽量保持结构化输出
2. Prompt 放文件，不写死到代码里
3. 可复用逻辑优先沉到 `services/`
4. 运行时行为尽量有日志

### 10.2 文档维护建议

1. 修改目录结构时同步更新 `PROJECT_STRUCTURE.md`
2. 修改流程时同步更新 `WORKFLOW_RUNTIME.md`
3. 修改架构原则时同步更新 `DESIGN_DETAILS.md`
